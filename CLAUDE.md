# CLAUDE.md

Lance a Lance: a mobile-first chess course in Brazilian Portuguese (11 modules, 59 short lessons, a Lichess puzzle trainer). It is an installable PWA served by the Node app in `server/`, with accounts and Postgres. It started as a claude.ai Artifact; that build is gone, and `docs/HISTORY.md` holds the full history and the product decisions, worth reading before changing behavior.

## Working with Mário (the owner)

- Talk to him in Portuguese. Code, code comments, commit messages and PRs in English.
- Never use em dashes or emojis in text he reads, and never in UI copy.
- CLI commands he has to run: always a single line.
- Git: NEVER squash commits. NEVER add `Co-authored-by` or any other co-authorship or attribution trailer to commits.
- Git: commit and push straight to `main`, no branch and no pull request. CI runs on every push to main, so check it after pushing and fix a red run right away.
- He is a developer and product person: explain trade-offs briefly, cite sources for chess facts when possible.

## Commands

- `pnpm install`, then `pnpm dev`.
- `pnpm typecheck` (tsc -b). Must pass before any commit.
- `pnpm validate`: builds every lesson many times and checks all positions and solutions. Scope with `ONLY=<lesson id prefix>` (e.g. `ONLY=m4-l4`) and `RUNS=<n>`. Use `RUNS=200` for new or changed lessons. `ONLY=treino` checks the trainer puzzles only.
- `pnpm build`: the installable build, into `dist/`. `pnpm build:server` compiles `server/` and `shared/` into `server/dist` (entry `server/dist/server/src/index.js`). `pnpm start` runs it from the repository root, where it serves `dist/` and the API.
- `pnpm gen:icons`: regenerates `public/*.png` from `assets/*.svg`. Only needed after editing those SVGs.
- E2E (Playwright, run `npx playwright install chromium` once): every script drives a running server, since the database is the only store. `pnpm e2e:prepare` (builds `dist/`), `pnpm build:server`, start a Postgres and the server (`DATABASE_URL=... COOKIE_SECURE=false PORT=3111 pnpm start`), then `URL=http://127.0.0.1:3111 pnpm e2e:<name>`: `walkthrough` (env: `DONE` = comma list of lesson ids to mark done, `MAX_LESSONS`, `SHOTS=1`, `SCHEME=dark`), `trainer`, `history`, `auto`, `home`, `pwa`, `game`, `account`, `reset`, `google`, `admin`. Outputs go to `tests/e2e/.out/`.
- `tests/e2e/env.cjs`: `signedIn(browser)` signs in as the test admin and wipes its progress; `completeLessons` and `attemptPuzzles` seed through the real endpoints. Reset, account and admin also need `tests/e2e/smtp-sink.cjs` and `SINK=`, because an address the admin liberates only gets a password through the link; Google needs `tests/e2e/google-sink.cjs`, `GOOGLE=` and, for the off switch check, `DATABASE_URL=`. `tests/e2e/accounts.cjs` holds becoming the admin, liberating an address and reading the link out of the sink.
- CI (`.github/workflows/ci.yml`) runs on pull requests and on pushes to main: typecheck, lint, validate, both builds, then every E2E except the walkthrough against the server, with a Postgres service and the mail sink. The walkthrough is `.github/workflows/walkthrough.yml` (same Postgres and server), triggered by hand, because it takes about twelve minutes. Do not move it into CI.

## Architecture in one screen

- Stack: React 19 + TypeScript + Vite 8 with vite-plugin-pwa, Tailwind 3.4 + shadcn/ui (Radix), lucide-react, react-chessboard 5.12.1 (`options` prop API), chess.js 1.4.0. Components use `React.FC`.
- Content is data. `src/content/curriculum.ts` lists modules and lessons. Each lesson is a `LessonDef` whose `build()` returns a fresh `Screen[]` with random examples, so repeating a lesson shows new positions.
- Screen kinds (`src/content/types.ts`): `explain`, `tap`, `tapAll`, `choice`, `drill`, `move`, `path`, `sequence`, `play`. Each has a step component in `src/components/lesson/steps/`.
- Position helpers in `src/content/lib/positions.ts`: `isLegalPosition` (also rejects the side not to move being in check), `randomVariant` (mirror files / flip colors), `withRandomKings`, `boardFor`, `afterMove`, `mateMoves`.
- Notation: always SAN followed by a Portuguese reading in parentheses, built by `describeMove` / `readMove` in `src/lib/chess/notation.ts` (e.g. `Nf3 (cavalo para f3)`, `Nbd2 (cavalo da coluna b para d2)`). Never hand-write readings that the helper can produce.
- Progress is rows in Postgres, and the server scores. The app reports facts (a lesson run, a puzzle attempt, a game's moves and its end) and shows the numbers the server answers with. Tables (migration `005_relational`): `player_stats` (XP, day streak, puzzle and game ratings and counts; the game counts and rating are recounted from `games` by `recountGames` on every restore and by migration 006, so no total exists without its games), `lesson_progress`, `lesson_runs`, `drill_records`, `puzzle_attempts`, `games` (one open game per user, a partial unique index). Nothing is kept in the browser; old localStorage keys are deleted on the first visit.
- `shared/` holds what both sides use: `scoring.ts` (stars, levels, day streak, Elo, XP per result, the "rated once both sides moved" rule), `games.ts` (levels, `replay`, `endOf`), `puzzles.ts` (puzzle ratings from `trainer.json`, so the server never takes one from the client) and `types.ts` (the read model `ProgressView`, the facts, the backup). The app imports it as `@shared/*`.
- Server routes: `GET /api/progress` (read model) and `POST /api/progress/reset`; `POST /api/lessons/runs`; `POST` and `GET /api/puzzles/attempts`; `/api/games` (start, `PUT :id/moves`, `POST :id/finish`, `DELETE :id` before both sides moved, history); `GET` and `POST /api/backup`. Every write is one transaction and answers with the new read model. A game's result is read off its replayed final position; only a resignation is taken on trust.
- Scoring: 10/5/2 points by attempt, tapAll 10 minus 3 per wrong tap (min 2) (`src/lib/progress/scoring.ts`, added up by the lesson player); stars at 90% and 70%, level n starts at 50·n·(n−1) XP. Puzzle and game ratings: Elo from 800, K=40 for the first 10 then 20, floor 100; a clean solve is a puzzle win; a draw is worth half.
- Client: `ProgressProvider` (`src/lib/progress/ProgressContext.tsx`) loads the read model and exposes `recordRun`, `recordPuzzle`, `games.*`, `reset` and the backup, all over `progressApi` (`src/lib/progress/api.ts`). `ApiOffline` (a dead fetch or a non-JSON answer) becomes `OfflineScreen`; there is no fallback store.
- Games (`src/components/game/GameScreen.tsx`): against Stockfish 19 lite single-threaded, shipped as published in `public/engine/` (GPL-3.0, not linted) and spoken to over UCI in a Web Worker (`src/lib/engine/`, `useGameEngines`). Levels 400 to 2400; below 1400 they are our own weakening, above it `UCI_Elo`. Moves are saved as they are played, so a reload or another device resumes the game. Assisted games show the full-strength engine's move and are never rated. History and review from `GET /api/games`.
- Accounts (`src/lib/auth/`): `AuthProvider` states are loading, offline, anonymous and signed-in. `Gate` in `App.tsx` shows `SignInScreen` while nobody is signed in, `OfflineScreen` when the API cannot be reached, and only then mounts `ProgressProvider` (keyed by the account), which waits for the first load. `/redefinir` is reachable without a session.
- Every screen has an address: `/`, `/treino`, `/partida`, `/partidas/<id>` (a finished game's review), `/licoes/<id>` (a reload starts the lesson again; its result shows at the same address), `/admin`, `/redefinir`. `src/lib/router.ts` is the whole router (History API, `useRoute`, `navigate`, `goBack`, which acts like the browser's back button when there is a screen of the app to go back to). A game's review loads through `GET /api/games/:id`, which answers 404 for anybody but its owner, the same as for a game that does not exist.
- Backup: `GET /api/backup` builds version 2 (the rows); `POST /api/backup` restores version 2, or converts version 1 (the old progress document and puzzle chunks) with `server/src/legacy.ts`, the same code migration 005 used. Keep reading version 1: old files are the way back.
- Test hooks: `main[data-solution]` (JSON with the answer for the current screen), `data-option-id`, `data-square`, `data-drill-target`, `data-promotion`, `window.__FAST_DRILL`, `main[data-game]` (phase, id in a review, side, turn, legal moves, hint, review ply), `data-game-rating`, `data-level`, `data-side`. Keep them working when adding screen kinds; the walkthrough depends on them.

## Rules for content changes

1. Short lessons: about 6 to 9 exercises, very little reading. Accessible Portuguese, no jargon without a one-line explanation.
   Copy says only what the screen does not: no cheering ("Isso!", "Boa!", "Muito bem") on top of the "Certo! +10 XP" title, no "tente de novo" under "Ainda não", no footer repeating how to move a piece or answer.
2. Every exercise must be verifiable: add a validator case in `scripts/validate-content.ts` if a new screen kind or rule appears.
3. Positions must be legal (`isLegalPosition`) unless the screen is an explicit teaching diagram.
4. Register new lessons in `curriculum.ts`; lesson ids are `m<module>-l<n>`.
5. Run `pnpm typecheck`, `ONLY=<id> RUNS=200 pnpm validate`, then `pnpm e2e:prepare` and a walkthrough of the touched lessons (`DONE` = every other lesson id, `MAX_LESSONS=<count>`).

## The server

- `server/src/` is Hono on Node, compiled by its own tsconfig. One process serves `dist/` and `/api` on one origin, so there is no CORS.
- Migrations are an ordered list in `server/src/migrations.ts`, applied at boot, each in one transaction. A migration may `run` code after its SQL (005 converts the old JSON progress with it). Never edit one that has shipped: add the next one.
- Passwords use the scrypt in `node:crypto`; sessions are opaque tokens kept only as a SHA-256 hash, in an httpOnly cookie. There is no signing secret by design, so do not add one.
- Signing up is only possible while there are no users: that first account claims the deploy and is the admin (`users.is_admin`). Every other account is created by the admin, by address, through `/api/admin/users` (`server/src/routes/admin.ts`, behind `requireUser` plus an admin check). Such an account has no password and no identity: its owner gets in with Google or by asking for a password on the sign in screen. Google refuses an address nobody liberated, for the same reason.
- The admin can promote, demote and delete, never itself, so the app is never left without an admin. There is no other privilege in the app: `isAdmin` opens `/admin` and nothing else.
- Signing in with Google is a second way in, not a replacement. `server/src/google.ts` builds the authorize URL and trades the code for an identity through the userinfo endpoint (no id token signature to verify). `user_identities` (provider, subject) points at a user, `users.password` is nullable for an account that only has a provider, and `signInWithIdentity` in `auth.ts` is the whole rule: known identity signs in, a new identity whose email Google reports as verified links to the account already holding that email, and otherwise creates one if signup allows. Never link on an unverified email: that is how somebody claims an address they do not own. Refusals redirect to `/?erro=<code>`, which `SignInScreen` turns into a sentence. Without `GOOGLE_CLIENT_ID` the whole thing, button included, is off.
- Password reset needs SMTP. Without `SMTP_HOST` the whole flow, interface included, turns itself off. Reset tokens live in `password_resets`, hashed like sessions, single use, 30 minutes, and spending one signs every device out inside the same transaction that changes the password.
- `/api/auth/forgot` answers the same whether or not the address has an account, so it cannot be used to find out who is registered. Keep it that way.
- Env: `DATABASE_URL` (required), `PORT`, `COOKIE_SECURE`, `STATIC_DIR`, `APP_URL`, the `SMTP_*` block and `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (`GOOGLE_AUTH_URL`, `GOOGLE_TOKEN_URL` and `GOOGLE_USERINFO_URL` exist only so the test can point at a fake Google). The `Dockerfile` builds both halves into one image for Easypanel; the container is stateless. The `GIT_SHA` build arg (Easypanel passes it) becomes `__APP_VERSION__` in the bundle, which the home footer shows; it is a build arg, not a runtime variable.
- Local: start a Postgres, then `DATABASE_URL=... COOKIE_SECURE=false pnpm dev:server`. `STATIC_DIR` defaults to `dist` in the directory the server starts from.
- The addresses the app answers are one list, `CLIENT_PATHS` in `shared/routes.ts`: the server serves the shell for them and a 404 (`public/404.html`) for anything else, the service worker falls back to the shell for them only (`vite.config.ts`), and `src/lib/router.ts` turns them into screens. A new screen is a new pattern there. Signing in with Google comes back to the address it started from (`?next=`, kept in a cookie and checked by `safeReturnPath`, so it is never an open redirect).
